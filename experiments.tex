\section{Experiments}\label{sec:experiments}

This section shows the execution of a large set of testcases
against the ABI of \cref{sec:interface}, instantiated
with different concrete and stubbed implementations of the blockchain peer, both
local and remote. Namely, the source code of Hotmoka
comes with $422$ testcases (including the two in \cref{fig:testcases}),
that have been developed in order to
verify the correctness of Takamaka smart contracts, including some from the standard
library shipped with Takamaka itself, and to provide a non-regression check
for the development of the Hotmoka application itself.
Such testcases can be found inside the \texttt{io-hotmoka-tests} module
of Hotmoka~\citep{hotmokacode}. The interested reader can reproduce
the experiments in this section by following the instructions at
\url{https://github.com/Hotmoka/hotmoka/blob/master/io-hotmoka-tests/README.md}.
The Git tag of the repository used for the experiments is \texttt{v1.12.5}.

We have run the testcases on an Intel Core i3-10110U\ $\times$\ 4
Linux Ubuntu 26.04 machine
with $16$ gigabytes of RAM, both for local and remote peers.
We ave used OpenJDK 25.0.4.1, Maven 3.9.12 and Tendermint 0.34.15.
Note, however, that the specific configuration of the testing machine
is largely irrelevant, since these tests use almost no RAM and their speed depends on the
block creation rate of the blockchain, not on the speed of the processor or Java interpreter,
except for the experiments with the stubbed peers.

The \texttt{HotmokaTest} superclass of all tests (\cref{fig:testcases})
initializes the blockchain for
testing, only once, before running all tests, as part of its \texttt{@BeforeAll} fixture.
It uses an environment variable \texttt{nodeType}
to communicate the kind of blockchain peer(s) that must be created.
Inside \texttt{HotmokaTest}, that variable is accessed and used to decide which
peer(s) must be created. \Cref{fig:nodeType} shows how this is performed. Methods
\texttt{mkTendermintNetwork} and \texttt{mkMokamintNetwork} create a blockchain whose peers
use Tendermint or Mokamint, respectively. The number of peers is also provided as an environment
variables to the tests: if $n\ge 1$ peers are required, then those methods return
the first of a network of a fully connected network of $n$ peers.
Method \texttt{mkStubbedNode} creates, instead, a single stubbed node, and
is used as default. In all three cases,
the peer is presented through its \texttt{io.hotmoka.node.api.Node} interface.
Furthermore, if a remote node is required,
the \texttt{mkRemoteNode} method adapts that interface first to a service and then to a remote
to such a service (\cref{fig:remote_peer}). In all cases,
the same \texttt{io.hotmoka.node.api.Node} interface is available to communicate to the blockchain peer.

\Cref{tab:experiments} shows the results of the testcases, executed against
different implementations of the peers of the testing blockchain. For instance, the first row shows
that the execution of the testcases against a local peer of a blockchain consisting of
that peer only, built over the Tendermint consensus engine, creating a block every $4000$
milliseconds, takes around three hours. All testcases succeed. The second row shows
that the reduction of the block creation rate to $3000$ milliseconds reduces the time for
running the tests to around two hours and a half. This time, the blockchain consists of
four peers, one of which receives the transaction requests for running the tests.
All tests succeed, also in this case. The third row runs the tests in the same
configuration as above, but against a remote peer.
The execution takes some minutes more, because of network delays, and all tests succeed.

The subsequent three rows in \cref{tab:experiments} run the testcases
against peers implemented over the Mokamint proof of space consensus engine.
The blockchain is first made of a single peer creating a block very $4000$
milliseconds, on average. Then it is made of four peers,
creating a block every $3000$ milliseconds. Finally, it is made of a single remote peer,
creating a block every $4000$ milliseconds and contacted through a network. The
interesting point, here, is that a Mokamint blockchain of more than one peer makes
some testcases fail ($67$ in our execution). This is because Mokamint has probabilistic
finality, like Bitcoin and like the first Ethereum, therefore the history of the
blockchain might change, until it finally stabilizes. Changes of history in the middle
of a testcase means that objects might ``disappear'' or change address or state, which makes
the testcase fail. Namely, the number of failing testcases is not constantly $67$,
but we have verified that it varies in different executions of the testcases, randomly.

Finally, the last two rows of \cref{tab:experiments} show experiments with a stubbed
peer, first local then remote. Stubbed peers do not keep any blockchain, therefore
there is no block creation rate for them. All tests succeed. The important aspect here is
that the execution time this time is very small, just a few minutes, which makes
these configurations adequate for continuous integration. In particular, the last configuration
is that used in the Github action triggered at every commit on the Hotmoka repository.

It is important to recall that the same testcases, unchanged, are used for all
configurations in \cref{tab:experiments}. This is a significant engineering simplification
and follows from the use of the same ABI for all configurations of the peer.
