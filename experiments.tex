\section{Experiments}\label{sec:experiments}

This section shows the execution of a large set of testcases
against the ABI of \cref{sec:interface}, instantiated
with different concrete and stubbed implementations of the blockchain peer, both
local and remote. Namely, the source code of Hotmoka
comes with $422$ testcases (including the two in \cref{fig:testcases}),
that have been developed in order to
verify the correctness of Takamaka smart contracts, including some from the standard
library shipped with Takamaka itself, and to provide a non-regression check
for the development of the Hotmoka application itself.
Such testcases can be found inside the \texttt{io-hotmoka-tests} module
of Hotmoka~\citep{hotmokacode}. The interested reader can reproduce
the experiments in this section by following the instructions at
\url{https://github.com/Hotmoka/hotmoka/blob/master/io-hotmoka-tests/README.md}.
The Git tag of the repository used for the experiments is \texttt{v1.12.5}.

We have run the testcases on an Intel Core i3-10110U\ $\times$\ 4
Linux Ubuntu 26.04 machine
with $16$ gigabytes of RAM, both for local and remote peers,
using OpenJDK 25.0.4.1, Maven 3.9.12 and Tendermint 0.34.15.
Note, however, that the specific configuration of the testing machine
is largely irrelevant, since these tests use almost no RAM and their speed depends on the
block creation rate of the blockchain, not on the speed of the processor or Java interpreter,
except for the experiments with the stubbed peers.

The \texttt{HotmokaTest} superclass of all tests (\cref{fig:testcases})
initializes the blockchain for
testing, only once, before running all tests, as part of its \texttt{@BeforeAll} fixture.
It uses an environment variable \texttt{nodeType}
to communicate the kind of blockchain peer(s) that must be created.
Inside \texttt{HotmokaTest}, that variable is accessed and used to decide which
peer(s) must be created. \Cref{fig:nodeType} shows how this is performed. Methods
\texttt{mkTendermintNetwork} and \texttt{mkMokamintNetwork} create a blockchain whose peers
use Tendermint or Mokamint, respectively. The number of peers is also provided as an environment
variables to the tests: if $n\ge 1$ peers are required, then those methods return
the first of a network of a fully connected network of $n$ peers.
Method \texttt{mkStubbedNode} creates, instead, a single stubbed node, and
is used as default. In all three cases,
the peer is presented through its \texttt{io.hotmoka.node.api.Node} interface.
Furthermore, if a remote node is required,
the \texttt{mkRemoteNode} method adapts that interface first to a service and then to a remote
to such a service (\cref{fig:remote_peer}). In all cases,
the same \texttt{io.hotmoka.node.api.Node} interface is available to interact with the blockchain peer
and testcases are programmed against that interface.

\Cref{tab:experiments} shows the results of the testcases, executed against
different implementations of the peers of the testing blockchain.
For each configuration, we have run the tests three times, in order to
identify potential variance in the results and execution time.

The first row in \cref{tab:experiments} shows
that the execution of the testcases against a local peer of a blockchain consisting of
that peer only, built over the Tendermint consensus engine, creating a block every $4000$
milliseconds, takes around three hours. All testcases succeed. The second row shows
that the reduction of the block creation rate to $3000$ milliseconds reduces the time for
running the tests to around two hours and a half. This time, the blockchain consists of
four peers, one of which receives the transaction requests for running the tests.
All tests succeed, also in this case. The third row runs the tests in the same
configuration as above, but against a remote peer.
The execution takes some minutes more, because of network delays, and all tests succeed.

The subsequent three rows in \cref{tab:experiments} run the testcases
against peers implemented over the Mokamint proof of space consensus engine.
The blockchain is first made of a single peer creating a block every $4000$
milliseconds, on average. Then it is made of four peers,
creating a block every $3000$ milliseconds. Finally, it is made of a single remote peer,
creating a block every $3000$ milliseconds and contacted through a network. The
interesting point, here, is that a Mokamint blockchain of more than one peer makes
some testcases fail (from $53$ to $113$ in our executions). This is because Mokamint has probabilistic
finality, like Bitcoin and like the first Ethereum, therefore the history of the
blockchain might change, until it finally stabilizes. Changes of history in the middle
of a testcase means that objects might \emph{disappear} or change address or state, which makes
the testcase fail. In our experiments,
almost all failures are due to an incorrect nonce in the transaction requests,
that do not match the current nonce in the target contract. This happens if the last transaction
request over that contract gets undone by a history change.
There is no special kind of testcases that fails. Instead, a testcase
is more likely to fail if it performs more transactions and therefore the probability
that at least one of them fails increases proportionally.
Another example of failure occurred in the \texttt{Bombing}\footnote{\url{https://github.com/Hotmoka/hotmoka/blob/master/io-hotmoka-tests/src/test/java/io/hotmoka/tests/Bombing.java}} testcase.
That testcase creates $500$ accounts, each funded with $500000$ coins. Therefore, the total funds in the
accounts is $500\cdot 500000$, that is, $250000000$. The testcase then executes
$1000$ random transfers between random accounts, with zero fees. At the end, it sums
the balances of the $500$ accounts and checks that it is still equal to $250000000$.
With Mokamint and four peers, this test sometimes fails with a message like
\texttt{expected: <250000000> but was: <249999996>}. This happens because of a history change
occurred during the access and computation of the sum of the balances of the $500$ accounts.

It is interesting to observe that the total execution time with failing tests
is rather variable: it can be longer as well as shorter than the time of the same testing configuration
with a single peer. In particular, if the failed transaction occurs during the
execution of the fixture of a testcase (that is, inside its \texttt{@BeforeAll} method) then
no testcase in the same file gets executed, the running time consequently
decreases and such non-executed testcases
are counted as failed in \cref{tab:experiments}. But it can also be the case that a testcase
was programmed to wait for an expected event, for instance, for a variable to reach an expected value,
which never occurs because some transaction fails.
As a consequence, such a testcase hangs for some time, until it gets terminated by a timeout.
In this case, the testcase runs longer.

In order to compare the timings of Tendermint and Mokamint, it must be clarified that
some testcases depend on transactions being processed by an exact time window (for instance,
auctions such as \texttt{BlindAuction}\footnote{\url{https://github.com/Hotmoka/hotmoka/blob/master/io-hotmoka-tests/src/test/java/io/hotmoka/tests/BlindAuction.java}}
and polls such as \texttt{PollWithTimeWindow}\footnote{\url{https://github.com/Hotmoka/hotmoka/blob/master/io-hotmoka-tests/src/test/java/io/hotmoka/tests/PollWithTimeWindow.java}}),
which is problematic for blockchains such as those based on Mokamint, whose
proof-of-space consensus creates blocks at an average rate but where each single block
may have a specific creation time that deviates significantly from the average rate.
Consequently, such testcases are programmed to greatly increase the time window if run on Mokamint,
in order to maximize the probability that transactions have been already committed by the time window.
As a consequence, timings with different blockchain implementations cannot be compared for such tests.
The two rows in \cref{tab:experiments}, whose implementation is marked with an asterisk, run
only the subset of testcases that do not depend on a time window and consequently provide a more
reliable comparison of the timings with different tools.

Finally, the last two rows of \cref{tab:experiments} show experiments with a stubbed
peer, first local then remote. Stubbed peers do not keep any blockchain, therefore
there is no block creation rate for them. All tests succeed. The important aspect here is
that the execution time this time is very small, just a few minutes, which makes
these configurations adequate for continuous integration. In particular, the last configuration
is that used in the Github action triggered at every commit on the Hotmoka repository.

It is important to recall that the same testcases, unchanged, are used for all
configurations in \cref{tab:experiments}. This is a significant engineering simplification
and follows from the use of the same ABI for all configurations of the peer.
Therefore, \cref{tab:experiments} shows that the same ABI can actually be used to run all tests
against different configurations and implementations of the blockchain. Still, there are threats to validity
that must be reported. First of all, timings for testcases that use a time window are difficult to compare between
implementations that create blocks at a \emph{fixed} or rather at an \emph{average} rate.
Another threat is related to the use of a stubbed
implementation, such as in the last two lines of \cref{tab:experiments}. That implementation lacks the
consensus and networking layers of a real blockchain, hence it is not covering the same amount of code
as a fully-fledged blockchain implementation. Finally, testcases ignore gas fees, differently from
what happens when run on a real blockchain.
